# v1.0.0 npm publish readiness assessment

This document evaluates whether `@devschile/chucao` is ready to publish its
first version to npm, and how well the current conventions scale as more
components are added.

## Summary

`package.json` is already at `1.0.0` and `docs/backlog.md` claims the
release-readiness backlog is closed. The component structure is consistent
across the 5 existing components. One concrete API-consistency gap was
found — `ch-button` was missing a `disabled` prop — and has been fixed as
part of this pass (see "Findings" below). A follow-up packaging review also
found that the build/publish surface (`exports` map) did **not** actually
support React/Vue consumption once installed from a real npm tarball: the
`exports` map was missing the `dist/components/*` subpaths that the React
wrapper imports internally, and the Vue wrapper never wired up custom
element registration. Both have since been fixed (see "Build/publish
surface" below). With those fixes applied, **this project is ready for a
first npm publish**, with a short list of deferred, non-blocking
follow-ups noted at the end.

## Documentation review

- **`docs/components.md` / `docs/using-the-library.md`**: cover `pnpm`
  scripts, project structure (`src/components`, `src/global`, `src/tokens`),
  the design-token single-source-of-truth (`chucao-tokens.json` → `toki` →
  `src/tokens/*`), and every consumption strategy the `package.json`
  `exports` map supports (lazy-loading `dist`, standalone
  `dist-custom-elements`, React, Vue, Svelte). They are accurate against the
  actual code: the documented `import '@devschile/chucao/ch-button'` and
  `@devschile/chucao/react` paths match `stencil.config.ts`'s
  `dist-custom-elements` and `reactOutputTarget` configuration. The
  component documentation previously only had a "Naming components" section
  covering tag prefixing; this has since been extended into "Naming & API
  conventions" (see `docs/components.md`) to give future component authors
  an explicit prop/event checklist, closing the main documentation gap found
  during this review. (This content originally lived in `README.md`; it was
  moved to `docs/` when the root README was slimmed down to a Spanish
  index.)
- **`DESIGN.md`**: documents the brand identity and the web design system
  (colors, typography, reference CSS components) that the Stencil
  components in `src/components/*` implement. It is a good reference doc
  but is not the place for component API conventions (that job now
  belongs to `docs/components.md`'s "Naming & API conventions" section).
- **`src/tokens/README.md`**: auto-generated by `toki`, documents the
  naming convention (`--kebab-case` CSS vars, `camelCase` JS exports,
  dotted paths in `types.ts`), scoped-styles behavior under Shadow DOM,
  and known limitations (composite tokens skipped in `tokens.css`). This
  is accurate and sufficient; no changes needed.
- **`docs/backlog.md`**: states the 1.0.0 backlog is "completed and
  shipped" with "no open items remain". This assessment did find one
  concrete gap (`ch-button` missing `disabled`), which has now been
  fixed; the backlog statement should be read as accurate for the scope
  it originally covered (badge variant, naming fix, boilerplate removal,
  version bump, npm metadata, build/test verification), not as a
  guarantee that zero gaps of any kind exist.

Observations:

- Every component follows the same file layout: `<name>.tsx`, `<name>.css`,
  `<name>.plugin.spec.tsx`, and an auto-generated `readme.md` produced by
  the `docs-readme` output target in `stencil.config.ts`. This is a solid,
  copy-pasteable template for future components.
- All components use `shadow: true` consistently, and CSS exclusively
  references design tokens (`var(--accent)`, `var(--text)`, `var(--border)`,
  etc. from `src/global/chucao.css` / `src/tokens/tokens.css`) rather than
  hardcoded values — good for a design system that will grow.
- Events are consistently prefixed `ch*` (`chClick`, `chInput`, `chChange`),
  and variant props are typed string unions exported alongside the
  component class (`ChButtonVariant`, `ChBadgeVariant`) — both good,
  reusable conventions, now written down explicitly in
  `docs/components.md`.
- **Gap found and fixed**: `src/components/ch-button/ch-button.tsx` only
  had `variant` and `chClick` — no `disabled`, while its sibling
  interactive components `ch-input`/`ch-select` both expose `disabled`.
  A consumer building a form with `ch-button` next to `ch-input`/`ch-select`
  could not disable it declaratively the same way. This has been fixed by
  adding `@Prop() disabled = false;`, wiring it to the native
  `<button disabled={this.disabled}>`, adding a `.btn:disabled` CSS rule,
  a Vitest assertion, and regenerating `readme.md`.
- Test coverage follows the same `@stencil/vitest` pattern in every
  component (`toEqualHtml` snapshot-style assertions plus behavior
  assertions like `spyOnEvent`), which is a good scalable baseline for new
  components.

## Scalability review

- **Token pipeline**: `chucao-tokens.json` → `toki` → `src/tokens/{tokens.css,tokens.ts,types.ts}`
  is a clean single source of truth. `src/global/chucao.css` imports
  `tokens.css` and layers short DESIGN.md-aliased vars (`--bg`, `--accent`,
  etc.) on top. New components only ever need to reference `var(--token-name)`
  in their CSS, so adding many more components does not require touching
  the token pipeline itself — it scales well.
- **Stencil output targets** (`stencil.config.ts`): `dist`,
  `dist-custom-elements`, `docs-readme`, `www`, plus React/Vue wrapper
  targets, are all declared once at the project level and apply
  automatically to every new component added under `src/components/*` —
  no per-component wiring is required beyond creating the folder, which is
  good for scale.
- **Prop/event conventions**: were previously only implicit (visible by
  reading existing components side by side). This is the main scalability
  risk identified — as the component count grows past 5, implicit
  conventions are easy to miss or diverge from, as evidenced by the
  `ch-button` `disabled` gap. This has now been made explicit in
  `docs/components.md`'s "Naming & API conventions" section as a checklist
  (tag prefix, event naming, variant typing, standard interactive prop
  set), which is the actionable scalability fix from this assessment.
- **Build/publish surface**: `package.json`'s `exports` map now supports
  the full dist / per-component / loader / react / vue consumption
  strategies documented in `docs/using-the-library.md`; `files` correctly ships only
  `dist/`, `dist-react/`, `dist-vue/`, `loader/`. This previously did
  **not** work end-to-end: the `exports` map lacked the wildcard
  `./dist/components/*` and `./dist/components` entries that
  `dist-react/components.js` and `dist-vue/index.js` import internally,
  which would have failed with `ERR_PACKAGE_PATH_NOT_EXPORTED` under a
  real npm install, and the Vue wrapper never registered its custom
  elements (`vueOutputTarget`'s `customElementsDir` option requires
  `includeImportCustomElements: true` to take effect). Both have been
  fixed in `package.json` and `stencil.config.ts`. The wildcard export
  entries mean this surface still does not need to change as components
  are added — new components remain automatically covered.

## Accessibility baseline (follow-up pass)

The accessibility gap originally deferred in this assessment (no built-in
label association or `aria-*` guidance on `ch-input`/`ch-select`) has since
been addressed: `ch-input` and `ch-select` now accept an optional `label`
prop that renders a `<label>` associated with the native control via a
generated `id`/`for` pair, and `ch-button` accepts a `label` prop applied as
`aria-label` on the native `<button>` for icon-only usage. `ch-button` also gained a visible
`:focus-visible` outline, since it previously had no focus style at all —
all interactive components (`ch-button`, `ch-input`, `ch-select`) rely on
native, keyboard-accessible elements, so Tab/Space/Enter navigation works
without extra wiring. This is now documented in `docs/components.md`'s "Naming & API
conventions" section under "Accessibility".

## Changelog (follow-up pass)

The `CHANGELOG.md` gap originally deferred in this assessment has since been
addressed: a `CHANGELOG.md` file was added at the project root, documenting
the `1.0.0` release (components, props/events, the accessibility baseline,
the design-token pipeline, and the `ch-button` `disabled` fix), following
the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format. Release
automation itself (e.g. auto-generating changelog entries from commits) is
still out of scope for this pass.

## Deferred / out of scope for this pass

The following gaps exist but were explicitly deferred per user decision;
they do not block a first npm publish but should be tracked for future
increments:

- **CI workflow**: no `.github/workflows` running `pnpm test` / `pnpm run build`
  on PRs.
- **Changelog automation**: entries are currently maintained by hand in
  `CHANGELOG.md`; no automated release/changelog generation tooling.

## Recommendation

**Go** — publish `1.0.0` to npm. The component structure is consistent,
the token pipeline and output-target setup scale well to additional
components, documentation accurately reflects the code, and the one
concrete API-consistency gap found (`ch-button` missing `disabled`) has
been fixed as part of this assessment, along with an explicit
"Naming & API conventions" checklist in `docs/components.md` so future components
stay consistent by default.
