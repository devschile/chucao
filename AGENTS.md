# AGENTS.md — project rules for AI agents and contributors

This file documents the conventions and guardrails for working on the Chucao
repo. Read it before making changes. It applies to human contributors and to
AI agents working in this repository.

## Where work comes from

**GitHub issues are the only source of truth for open work.** There is no
backlog file, roadmap document, or task list checked into this repository — if
something has no issue, it is not planned yet.

- Before starting anything, find the issue it belongs to. If there is none,
  **open one first** and settle the approach there before writing code. The
  templates live in `.github/ISSUE_TEMPLATE/` and cover bug reports, component
  proposals, and documentation.
- A minor correction (a typo, an obvious one-line fix) can go straight to a pull
  request — see `CONTRIBUTING.md`. Anything larger needs an issue first.
- Issues labelled `discussion` are ideas that still need a decision. **Do not
  implement them.** Comment on the issue instead.
- Reference the issue from the pull request: `Closes #123` when the PR finishes
  it, `Refs #123` when it only advances it.
- **Never reintroduce a checked-in backlog, roadmap, or TASKS file.** Planning
  belongs in issues, where the whole community can see and pick it up. A file
  in the repo drifts from reality and splits the source of truth in two.
- For what already shipped, read `CHANGELOG.md` and the git history rather than
  a planning document.

## Documentation rules

- **The root `README.md` must be written in Spanish and kept concise.** Do
  not expand it with long technical content and do not translate it to
  English. It is an index + community-facing overview, not the full docs.
- **Docs under `docs/` may be in English or Spanish.** English is preferred
  for technical/developer content (`components.md`, `using-the-library.md`,
  `testing.md`); Spanish is preferred for brand/community content
  (`assets.md`). Keep each doc consistent in the language it starts with.
- When adding documentation, prefer splitting content into `docs/` files over
  growing the root `README.md`. Update `README.md`'s documentation table
  when adding a new doc file.
- `DESIGN.md` (brand identity + web design system) lives at the root and is
  referenced from `README.md`; do not move it.
- `src/tokens/README.md` is auto-generated by `toki` — never edit it by hand.

## Design tokens

- Files under `src/tokens/` (`tokens.ts`, `tokens.css`, `tokens.d.ts`,
  `types.ts`) are **generated by `toki` from `chucao-tokens.json` — never
  edit them by hand**. To change tokens, edit `chucao-tokens.json` and run the
  `toki` pipeline.
- `src/global/chucao.css` is the single stylesheet bundled into every build
  (`globalStyle`); it imports `tokens.css`. Components must reference tokens
  via `var(--token-name)` — never hardcode colors/values.

## Component conventions

Every component lives in its own folder under `src/components/<name>/` with
this layout: `<name>.tsx`, `<name>.css`, `<name>.plugin.spec.tsx`, and an
auto-generated `readme.md` (produced by the `docs-readme` output target — do
not hand-edit it).

Follow these API conventions (documented in `docs/components.md`):

- Tag prefix: `ch-` (e.g. `ch-input`), never `chucao`/`stencil` alone.
- Custom events: prefix with `ch` + camelCase (`chClick`, `chChange`,
  `chInput`), mirroring the native event they wrap.
- Variant props: type as a string union and export it as a named type
  alongside the component class (`ChButtonVariant`, `ChBadgeVariant`).
- Standard interactive props: `disabled`, `required`, `name`, and `value`
  (`@Prop({ mutable: true })`) where applicable, reflected straight onto the
  native element.
- Accessibility: use native, keyboard-accessible elements inside the shadow
  root; expose labels via a `label` prop (`id`/`for` pair for
  `ch-input`/`ch-select`, `aria-label` for `ch-button`); keep a visible
  `:focus-visible` style on interactive elements.
- All components use `shadow: true`.

## Commands

- `pnpm install` — install dependencies (pnpm only; `package.json` pins
  `packageManager`).
- `pnpm start` — dev server (watch + serve).
- `pnpm run build` — Stencil build + React/Vue wrapper builds.
- `pnpm test` / `pnpm run test:coverage` — component tests / coverage.
- `pnpm lint` (oxlint) / `pnpm lint:fix` — linting.
- `pnpm run format` / `pnpm run format:check` — Prettier.
- `pnpm run generate` — `stencil generate` scaffolding.
- `pnpm run release` — `release-it` release (creates a version tag; the CI
  workflow `.github/workflows/release.yml` builds, lints, tests, and publishes
  to npm when a version tag is pushed).
- **Always add a release description** — after `pnpm run release`, the CI
  workflow creates the GitHub Release with auto-generated notes. Edit it with
  `gh release edit <version> --notes-file …` and a hand-written description
  following the format of previous releases (e.g. 1.5.1): a `# Chucao <version>`
  heading, a one-line summary, `##`-sectioned changes with `- **`item`** — …`
  bullets, a `## Quality` block (tests/lint/build), and the `**Full Changelog**`
  comparison link. Do this before the release is considered done.

**Always run `pnpm lint` and `pnpm test` after making changes** and keep them
green — the release pipeline depends on them.

## General conventions

- 2-space indentation, LF line endings (see `.editorconfig`).
- Do not add code comments unless asked.
- Follow existing code and file-organization patterns; when adding a new
  component, copy the structure of an existing one.
- Do not commit unless explicitly asked.
